# 2. Confirmed Current Packaging Gap

The current production package is not yet a complete standalone application.

The existing Electron main process:

```text
apps/desktop/src/main/index.ts
```

currently expects a pre-existing file:

```text
%LOCALAPPDATA%\PersonalCodexAgent\daemon.json
```

It reads the daemon URL and token from that file, but it does not start, supervise, restart, or stop the daemon itself.

The existing development supervisor starts:

1. The local daemon.
2. The Vite renderer.
3. Electron.

However, that supervisor is designed for development and is not part of the installed application.

The current packaging script:

```text
scripts/package.ts
```

copies only the compiled desktop output into an Electron package. It does not yet create a full installer and does not establish a complete production daemon lifecycle.

The current daemon build also uses external package resolution:

```text
--packages=external
```

That means the daemon cannot simply be copied into the installed application without ensuring all required runtime packages and native modules are correctly included.

This prompt must resolve these exact issues.

# 6. Production Daemon Lifecycle

Implement a real production daemon manager in the Electron main process.

Create a focused component such as:

```text
apps/desktop/src/main/daemon-manager.ts
```

The exact filename may differ, but the responsibility must be isolated and testable.

## Required daemon startup sequence

On production launch:

1. Obtain a single-instance application lock.
2. Resolve the application data directory.
3. Create required directories.
4. Initialize structured desktop logging.
5. Check for stale daemon metadata.
6. Confirm whether a recorded process is alive and application-owned.
7. Remove only stale metadata.
8. Start the bundled daemon.
9. Pass the correct writable application-data directory.
10. Use a dynamically selected loopback port.
11. Generate or receive a fresh secure token.
12. Wait for a definite daemon-ready signal.
13. Verify `GET /health`.
14. Verify the returned daemon version is compatible with the desktop version.
15. Save restricted diagnostic connection metadata.
16. Expose connection information to the renderer through the preload bridge.
17. Only then load the full application interface.

Do not rely on a daemon that happened to be left running by development mode.

## Recommended process architecture

Prefer a dedicated Electron `utilityProcess` or another properly supervised application-owned child process.

The production daemon must use the Node runtime already included with Electron or another runtime packaged inside the application.

Do not require a globally installed Node.js executable.

Do not start the daemon by invoking:

```text
node
npm
npx
tsx
```

from the user’s system.

The final implementation may use:

* `utilityProcess.fork`.
* A bundled Node-compatible child entry point launched through Electron.
* Another Electron-supported isolated process approach.

Choose the method that gives the best combination of:

* Process isolation.
* Native module compatibility.
* Controlled shutdown.
* Reliable packaging.
* Crash detection.
* Logging.
* Windows compatibility.
* Testability.

Document the final choice.

## Daemon readiness

Do not use a fixed sleep as the only readiness check.

Use one or more of:

* Structured IPC ready message.
* Structured stdout event.
* Bounded polling of the health endpoint.
* Direct process message event.

The startup must have a timeout and a clear error state.

## Daemon crash handling

When the daemon exits unexpectedly:

* Record the exit code.
* Record sanitized stderr.
* Notify the renderer.
* Disable actions that require the daemon.
* Attempt only a bounded number of automatic restarts.
* Use delay or backoff between attempts.
* Avoid infinite restart loops.
* Offer a manual retry.
* Offer diagnostics export.
* Offer safe-mode startup when appropriate.

## Shutdown

When the application exits:

1. Stop active agent work safely where possible.
2. Request graceful daemon shutdown.
3. Wait for a bounded shutdown period.
4. Terminate only the application-owned process if necessary.
5. Clean connection metadata.
6. Close log streams.
7. Ensure no daemon, Codex, Git, test, or helper processes remain orphaned.

Do not kill unrelated processes by executable name.
