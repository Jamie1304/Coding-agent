# Phase 3 — Add Mandatory Step-Gated Execution, Live Runtime Testing, Project Knowledge Tracking, Documentation Maintenance, and GitHub Checkpoints

You are continuing development of the existing **Personal Codex Agent**.

Work from the current repository root.

Your task is to inspect the existing implementation and add a mandatory execution system that forces every approved development run to proceed in strict chronological steps.

For every run, the agent must:

1. Turn the approved request into a detailed chronological step plan.
2. Complete only one step at a time.
3. Implement the step.
4. Add or update tests for the step.
5. run the real application from a terminal.
6. Inspect all terminal output and runtime errors.
7. Test the real UI, API, routes, buttons, processes, and integrations affected by the step.
8. Stop and restart the application.
9. Repeat the relevant runtime tests after restarting.
10. Automatically diagnose and fix discovered errors.

14. Create a focused Git commit for the completed step.
15. Push the commit to GitHub.
16. Update the active pull request with progress and evidence.

The agent must never skip ahead to a later implementation step while an earlier step is incomplete, failing, untested, undocumented, uncommitted, or not pushed to GitHub.

# 2. Core Behavioral Rule

Add this mandatory rule to the agent’s execution policy:

> Every approved implementation request must be converted into a chronological, step-based execution plan. A step may advance only after its implementation, automated tests, real runtime tests, restart tests, diff review, documentation updates, project-knowledge updates, Git commit, Git push, and pull-request checkpoint have all completed successfully.

# 9. Instant Error-Correction Loop

When a runtime error appears, the agent must immediately pause step advancement.

Use:

```text
Detect runtime error
→ Capture complete evidence
→ Normalize signature
→ Identify affected component
→ Inspect relevant code
→ Form a root-cause hypothesis
→ Apply focused correction
→ Add or update regression test
→ Run focused test
→ Restart affected process
→ Repeat real runtime interaction
→ Verify error is gone
→ Run full affected validation
```

Do not continue to later work while the current runtime error remains unresolved.

## 9.1 Bounded intelligent retry

Do not loop blindly.

Record each correction attempt:

```ts
export interface RuntimeCorrectionAttempt {
  errorSignature: string;
  attemptNumber: number;
  hypothesis: string;
  evidence: string[];
  filesChanged: string[];
  regressionTestsAdded: string[];
  result: "resolved" | "improved" | "unchanged" | "worse" | "blocked";
}
```

When attempts are non-improving:

* Stop repeating the same fix.
* Start an independent diagnostic review.
* Compare with prior attempts.
* Revert harmful attempts.
* Escalate to a stronger configured model when appropriate.
* Mark the step blocked when an external requirement prevents resolution.
* Never report the step as complete.

# 17. Semantic Versioning Policy

Every successful approved implementation run must produce a version decision.

Use semantic versioning:

* Patch: backward-compatible bug fix, documentation correction tied to a release, internal improvement, or maintenance change.
* Minor: backward-compatible user-visible feature.
* Major: breaking change.

For pre-1.0 projects, document the project’s chosen interpretation and apply it consistently.

Create a structured version decision:

```ts
export interface VersionDecision {
  previousVersion: string;
  nextVersion: string;
  changeType: "patch" | "minor" | "major";
  reasons: string[];
  breakingChanges: string[];
  migrationRequired: boolean;
}
```

The version must not be finalized before implementation and tests are complete.

Use this sequence:

1. Predict version impact during planning.
2. Complete implementation.
3. Validate actual impact.
4. Confirm the version decision.
5. Update version files.
6. Update changelog.
7. Update README.
8. Update project knowledge.
9. Commit version and release documentation.
10. Push.
11. Tag after merge and successful release validation.
