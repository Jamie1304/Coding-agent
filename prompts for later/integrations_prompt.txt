````markdown
# Personal Codex Agent — Universal AI CLI, Git and GitHub Desktop Integration

## Mission

Extend the existing Personal Codex Agent into a complete Windows-first desktop application that allows the user to install, authenticate, configure, update, use, monitor and remove AI coding agents and Git/GitHub integrations entirely from the graphical application.

The user must not need to open PowerShell, Command Prompt, Git Bash, npm, GitHub CLI or any other terminal for normal usage.

The final product must be distributable as a Windows `.exe` installer. After launching the installer and application, the user must be able to complete the entire setup through the GUI.

The application must support current and future AI coding CLIs through a provider-adapter architecture rather than hardcoding one provider into the application.

Do not remove or weaken the existing approval workflow:

- The application must still convert requests into reviewed specifications.
- The user must still approve the frozen prompt before implementation.
- Code must still run inside isolated Git worktrees where appropriate.
- Tests, diffs, quality gates and evidence reports must remain active.
- GitHub and deployment stages must remain skipped honestly when they are not configured.
- No provider may silently bypass the application's approval system.

## Existing application context

The existing project is:

- Windows-first.
- Built with Electron, React, TypeScript and a loopback-only Node daemon.
- Uses SQLite for run history.
- Contains Git, GitHub, deployment, quality-gate and evidence-report adapters.
- Contains a VS Code workspace bridge.
- Uses Codex app-server as the primary coding-agent integration.
- Has setup, doctor, testing, packaging and security documentation.
- Currently expects optional integrations such as VS Code, Codex and GitHub CLI to be installed separately.
- Currently has development commands such as `npm run dev`, `npm run build`, `npm test`, `npm run doctor` and `npm run package`.

Preserve the existing architecture and conventions. First inspect the repository and identify the actual file structure, current APIs, database schema, renderer routes, daemon endpoints, packaging configuration and test setup. Do not blindly create a parallel architecture.

## Primary user outcome

From the desktop application, the user must be able to:

1. Install missing prerequisites.
2. Install supported AI coding CLIs.
3. Sign in to each provider through a browser, device-code flow or secure API-key form.
4. See whether each provider is installed, authenticated, available and healthy.
5. Select an AI provider and model from the application.
6. Start, resume, pause, cancel and inspect agent sessions.
7. Stream agent output, tool calls, file changes, permission requests and errors in the application.
8. Run agents inside the application's existing isolated worktree workflow.
9. Review diffs and test results.
10. Connect GitHub without manually using `gh auth login`.
11. Clone, browse and manage GitHub repositories.
12. Create branches, commits, pull requests and issues.
13. View pull-request checks and GitHub Actions results.
14. Push changes to GitHub only after explicit confirmation.
15. Install, update and uninstall supported integrations through the GUI.

## Important design principle

Do not claim that every AI CLI supports the same feature set.

Each provider must expose explicit capabilities such as:

```ts
type ProviderCapabilities = {

  headless: boolean;
  streaming: boolean;
  jsonOutput: boolean;
  jsonlOutput: boolean;

  appServer: boolean;
  modelListing: boolean;
  sessionResume: boolean;
  sessionFork: boolean;
  cancellation: boolean;
  worktrees: boolean;
  mcp: boolean;
  permissionRequests: boolean;
  fileChanges: boolean;
  shellExecution: boolean;
  usageReporting: boolean;
  browserAuthentication: boolean;
  deviceAuthentication: boolean;
  apiKeyAuthentication: boolean;
};
````

The UI must always show unsupported features honestly. For example:

* “Streaming unavailable for this provider.”
* “Session resume is not supported.”
* “This provider can run read-only reviews but cannot safely mediate write permissions.”
* “This provider is installed but not authenticated.”
* “This provider requires an API key for headless mode.”

## Provider integration strategy

Implement the following protocol layers.

### 1. Codex app-server adapter

Use Codex app-server for the deepest Codex integration.

Support:

* Local app-server startup.
* JSONL-over-stdio transport.
* Optional localhost WebSocket transport.
* `initialize`.
* `account/read`.
* `account/login/start`.
* Browser login.
* Device-code login.
* API-key login.
* `account/login/completed`.
* `account/updated`.
* `thread/start`.
* `thread/resume`.
* `thread/fork`.
* `turn/start`.
* `turn/steer`.
* `turn/interrupt`.
* Streaming turn and item events.
* File changes.
* Diffs.
* Command execution events.
* Permission requests.
* User-input requests.
* Model discovery.
* MCP status.
* Thread history.
* Session cancellation.
* Clean process shutdown.

Prefer app-server over parsing the Codex terminal UI.

Use `codex exec --json` as a fallback for simple non-interactive operations when app-server is unavailable.

Never read or copy Codex tokens directly from `auth.json`. Use Codex’s supported authentication methods and app-server account endpoints.

### 2. Generic ACP adapter

Implement an Agent Client Protocol adapter for providers that expose ACP over stdio.

The ACP adapter must:

* Launch the provider as a child process.
* Communicate over JSON-RPC.
* Support newline-delimited JSON messages.
* Send `initialize`.
* Negotiate protocol and capabilities.
* Support `auth/login` when advertised.
* Support `session/new`.
* Support `session/prompt`.
* Support `session/update`.
* Support `session/cancel`.
* Support permission requests.
* Support session resume when advertised.
* Support session close when advertised.
* Capture stderr separately from protocol stdout.
* Reject malformed protocol messages.
* Detect process hangs and crashes.
* Kill the complete process tree on cancellation.
* Normalize ACP events into the application’s shared event schema.

Implement ACP v1 first. Add feature detection for future ACP versions rather than assuming version-specific behavior.

Do not confuse Agent Client Protocol with unrelated protocols using the ACP abbreviation.

### 3. JSON/JSONL CLI adapter

For providers without ACP or app-server support, implement a secure CLI adapter.

The adapter must support:

* Version detection.
* Command discovery.
* Safe argument arrays.
* Hidden Windows process execution.
* Working-directory selection.
* Environment injection.
* Prompt delivery through arguments or stdin.
* JSON output parsing.
* JSONL streaming parsing.
* Plain-text fallback.
* Exit-code handling.
* Timeout handling.
* Cancellation.
* Process-tree cleanup.
* Session ID extraction.
* Resume support where available.
* Redaction of secrets and sensitive paths.
* Provider-specific permission flags.

Do not use `shell: true` by default.

On Windows, implement safe handling for `.cmd` launchers and test command quoting thoroughly.

### 4. One-shot text adapter

Support providers such as Aider that offer useful one-shot scripting but do not provide a stable event protocol.

This adapter must:

* Run the provider in a worktree.
* Capture stdout and stderr.
* Display output as plain text.
* Detect file changes through Git.
* Detect commits created by the provider.
* Apply application-level approval before the provider is allowed to write.
* Mark event-level tool visibility as unavailable.
* Never pretend that unobserved provider actions were individually approved.

## Approval and safety integration

Every provider must use the existing application approval lifecycle:

1. User submits a request.
2. Application creates a draft specification.
3. User reviews and revises it.
4. Application freezes the approved prompt.
5. Application creates or reuses an isolated Git worktree.
6. Application starts the selected provider inside that worktree.
7. Provider receives only the approved prompt and permitted context.
8. Provider permissions are constrained according to the application approval mode.
9. Tool calls and file changes are streamed into the UI.
10. The user can approve, deny, pause or cancel when supported.
11. Tests and quality gates run.
12. Diff and evidence report are generated.
13. GitHub actions remain confirmation-gated.

Never automatically pass any of the following flags unless the user explicitly selects an equivalent unsafe mode:

* `--yolo`
* `--full-auto`
* `--allow-all`
* `--allow-all-tools`
* `--allow-all-paths`
* `--trust-all-tools`
* `--always-approve`
* `--dangerously-skip-permissions`
* Any provider-specific unrestricted permission mode

If a provider cannot safely support application-level permission mediation:

* Allow it for read-only review mode if safe.
* Allow write mode only inside a disposable isolated worktree with strict provider flags.
* Otherwise mark write execution as unavailable.
* Explain the limitation in the UI.
* Do not pretend that unsafe execution is equivalent to normal approval.

### Security tests

Verify:

* Renderer cannot access Node APIs.
* Renderer cannot spawn processes.
* Renderer cannot read secrets.
* Daemon only listens on loopback.
* Invalid daemon tokens are rejected.
* Provider arguments cannot inject commands.
* Secrets are redacted from UI, logs and evidence reports.
* Paths cannot escape the selected worktree.
* GitHub tokens are not written to command arguments.
* Remote provider catalogs cannot execute arbitrary installers.
* Dangerous Git and GitHub operations require confirmation.
* Provider write operations cannot bypass the application approval gate.

## Definition of done

This work is complete only when:

* The `.exe` launches without a terminal.
* The daemon starts automatically.
* The setup wizard detects missing prerequisites.
* Providers can be installed from the GUI.
* Providers can be authenticated from the GUI.
* At least Codex, Claude Code, Gemini CLI, Grok Build, GitHub Copilot CLI and GitHub work end-to-end.
* The architecture supports OpenCode, Qwen, Cline, Cursor, Kiro and Aider.
* Git operations can be performed through the application.
* GitHub repository, branch, commit and pull-request workflows work through the application.
* No user is required to run `npm`, `codex login`, `gh auth login` or equivalent commands for normal setup.
* Secrets are protected and redacted.
* Approval gates remain active.
* Worktree isolation remains active.
* Dangerous operations require confirmation.
* Missing or unsupported capabilities are shown honestly.
* All tests pass.
* The packaged application works on a clean Windows installation.
* Documentation accurately describes the current state.

  * Tests executed.
