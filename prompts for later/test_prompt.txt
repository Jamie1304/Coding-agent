You are a senior Windows-first full-stack engineer, QA engineer, security reviewer, and release engineer.

Your task is to perform a complete audit of the existing “Personal Codex Agent” repository, identify bugs and inconsistencies across the application and codebase, fix all safe in-scope issues, and verify the result.

This is an audit-and-repair task only. Do not expand the product scope or introduce unrelated features.

## Project context

Personal Codex Agent is a Windows-first, single-user desktop application consisting of:

- Electron desktop client
- React renderer
- Loopback-only Node daemon
- Typed API between renderer and daemon
- VS Code workspace bridge
- SQLite run history
- Deterministic orchestration
- Prompt review and approval workflow
- Codex app-server integration
- Isolated Git worktrees
- Git and GitHub adapters
- Quality gates
- Deployment and rollback adapters
- Markdown and JSON evidence reports

The application must preserve this core rule:

“No repository write or Codex implementation turn is allowed before the user approves a prompt revision.”

GitHub and deployment stages must continue to be skipped honestly when they are not configured.

The project is Windows-first and must remain usable through the packaged `.exe` without requiring users to manually use the terminal for normal setup and operation.

Inspect the entire repository and correct:

## Phase 2: audit the application

### A. Application startup and lifecycle

Verify:

- Development startup works from a path containing spaces.
- The packaged Windows application starts correctly.
- The daemon starts, reports readiness, and shuts down cleanly.
- The Electron app handles daemon startup failure.
- Ports are selected and released correctly.
- Stale daemon processes do not remain after application exit.
- Restarting the application does not corrupt state.
- Multiple startup attempts do not create duplicate daemons or conflicting listeners.
- Errors are shown in the UI instead of being silently swallowed.
- Unhandled promise rejections and uncaught exceptions are handled appropriately.

### B. Electron security

Verify:

- `contextIsolation` is enabled.
- `nodeIntegration` is disabled in the renderer.
- The renderer cannot access arbitrary Node or filesystem APIs.
- The preload bridge exposes only the intended typed methods.
- IPC channels are validated.
- Renderer input cannot invoke arbitrary shell commands.
- External URLs are handled safely.
- Windows paths are validated and normalized.
- Secrets and authentication tokens are never exposed to the renderer unnecessarily.
- Development-only security bypasses are not enabled in production packaging.
- The daemon accepts only authenticated loopback requests.

Fix any security regression without weakening the existing security model.

### C. Renderer and UI consistency

Test every major screen and workflow, including:

- First launch
- Setup and Connections
- Project or folder selection
- Workspace verification
- Prompt submission
- Material-question handling
- Prompt revision
- Prompt approval
- Execute workflow
- Run history
- Run details
- Diff review
- Evidence reports
- GitHub stages
- Deployment stages
- Error states
- Empty states
- Missing-integration states
- Cancelled and failed runs

Check for:

- Buttons that do nothing
- Incorrect navigation
- Broken loading states
- Stale data after mutations
- Forms that lose input
- Incorrect disabled/enabled states
- Missing validation
- Inconsistent terminology
- Inconsistent date/time formatting
- Incorrect status colors or labels
- Errors that are not actionable
- Missing retry actions
- Duplicate notifications
- Race conditions during refresh
- Accessibility problems
- Text overflow or layout problems in Windows packaging
- UI behavior that differs between development and packaged builds

Do not redesign the application. Fix correctness and consistency issues while preserving the existing design.

### D. Prompt review and approval workflow

Verify the complete state machine:

1. User submits an incomplete request.
2. The application identifies material questions.
3. The user revises or answers questions.
4. A frozen prompt/specification is produced.
5. The user explicitly approves the revision.
6. Only then may repository-writing or Codex execution begin.
7. The execution runs in an isolated worktree.
8. Results, tests, diffs, and evidence are recorded.

Check that:

- Approval cannot be accidentally bypassed.
- Revisions invalidate previous approval when appropriate.
- The frozen prompt cannot be silently modified.
- Double-clicking approval does not start duplicate runs.
- Refreshing the UI does not lose workflow state.
- Cancelled runs have a consistent final state.
- Failed runs preserve useful diagnostics.
- Completed runs cannot be incorrectly shown as running.
- Run state survives application restart.
- Run history accurately reflects the actual execution state.

### E. Daemon and API contracts

Inspect every daemon endpoint and compare it with:

- Renderer API calls
- Preload types
- Shared TypeScript types
- Request validation
- Response validation
- Database models
- Tests
- Documentation

Look for:

- Mismatched property names
- Optional fields treated as required
- Different status values in different modules
- Inconsistent HTTP status codes
- Inconsistent error shapes
- Missing validation
- Incorrect serialization of dates, paths, errors, and enums
- APIs that return different shapes on success and failure
- Endpoints that do not handle malformed input safely
- Missing authentication checks
- Duplicate or conflicting constants
- Dead endpoints
- UI calls to endpoints that no longer exist

Make the API contract internally consistent and add tests for corrected behavior.

### F. Codex integration

Verify:

- Authentication diagnostics are accurate.
- Missing Codex installation or authentication is reported clearly.
- The app-server process is launched safely.
- Windows executable paths are handled correctly.
- Arguments are passed without shell-injection risk.
- Streaming output is parsed correctly.
- Malformed or partial messages do not crash the daemon.
- Process exit codes are handled correctly.
- Timeouts work.
- Cancellation works.

- Run identifiers remain consistent across UI, daemon, database, worktree, and evidence output.

## Phase 3: classify and repair findings

Classify each finding as:

- Blocker: prevents startup, execution, data safety, or release
- Critical: security, approval bypass, data corruption, or destructive behavior
- Major: broken primary workflow or serious integration failure
- Minor: limited defect or inconsistency
- Cosmetic: wording, formatting, or low-impact presentation issue

Fix all Blocker, Critical, and Major issues that are within the repository and task scope.

Fix Minor and Cosmetic issues when the fix is low-risk and does not expand scope.

For every fix:

1. Identify the root cause.
2. Make the smallest safe code change.
3. Add or update a regression test.
4. Run the narrowest relevant test first.
5. Run the complete validation suite afterward.
6. Confirm that the change does not weaken security or approval controls.

If an issue cannot be fixed safely because it depends on unavailable software, external credentials, or an environment limitation, document it precisely and implement the best safe fallback or diagnostic behavior.
